# Review session

This skill coordinates the review loop. The spawned session performs each review with a review skill available in its own harness. The invoking session owns the loop and normally owns the change; if another session owns the change, record its exact Relay slug and route findings to it. The reviewer is read-only. This differs from an ordinary `handoff`, which transfers ownership.

The loop runs to a stop level: one pass, no real defects, or fully clean. When `review-loop` invokes this skill, use the level it passes. Otherwise judge the level the way `review-loop` describes, from how costly a defect that survives the review would be, state it with its reason, and proceed; the user overrides. Below, **clean** means the latest round met that level.

Read `new-session` for process launch, session naming, resume, and worktree
boundaries. Read `session-message` for channel selection, registration,
listeners, sends, acknowledgements, and conditional wakes. Its announced
preflight fallback is available when both sessions have reachable native
addresses or share a tmux server. Keep the selected channel through all review
rounds.

## Prepare the review

1. Identify the author session and the change to review. Default the reviewer to this session's CLI; honor a different CLI or model the user names. Verify that the executable exists and that the chosen harness can invoke a suitable review skill. Use [reviewer routing](references/reviewer-routing.md) for the harness-specific choice. If the selected harness has no usable review skill, set one up when permitted and verify its discovery; otherwise explain the blocker rather than silently using a generic prompt or substituting a harness.
2. Select the channel before launch through `session-message`. Preserve any existing Relay slug assigned to this session. If the author is another session, get its exact Relay slug or reachable native or tmux address for the selected channel; do not guess it.
3. Pin an immutable target for each round: the repository root, target kind, base commit, tip commit or review commit, and any user-supplied review criteria. Resolve refs to full commit IDs before sending. For a branch, identify its intended merge target from the user, pull request metadata, or an established repository workflow; ask when it is unclear. A tracking upstream of the same feature branch is not its merge target. Resolve the merge base with that target and pin it, then review the complete change that would merge from the feature tip. The reviewer uses the pinned IDs rather than resolving moving branch names again. A branch name alone is not a review target.
4. Do not send the reviewer into the author's live worktree. A reviewer can inspect committed objects from the repository root. If its native review skill needs a checkout, it creates its own clean, detached worktree at the pinned tip and removes it after closure. For uncommitted work, the author must first provide an immutable review snapshot that includes staged, unstaged, and untracked intended changes; record what it contains and what it excludes. Do not claim a branch review covers changes outside that snapshot. Do not alter the author's index or branch merely to make a review target.
5. Launch a named, resumable reviewer session in its own tmux window using `new-session`. Keep its initial prompt short but explicit: name the pinned target as context, the selected review skill, the chosen channel and its exact addresses as `session-message` directs, an instruction to load the `session-message` skill and follow it for its side of the channel, the read-only boundary, and the round protocol below. Tell it to establish its side of the selected channel and wait for the first review request. The prompt itself is not a duplicate request. It reads and follows the repository's agent instructions and the user's global ones, named by path in the prompt since its CLI may load a different global file, reads the relevant committed design documents, then uses its review skill, holding the change to those instructions as well. It must report every actionable finding through the selected channel, never use a review command's fix/post option, and remain online awaiting another round until told to close. A simple review needs no handoff document; use one in the main checkout's `do_not_commit` area when the change needs durable context. The reviewer must not inspect another session's linked worktree, edit files, commit, merge, post comments, or send a final user recap while rounds remain.

## Run rounds

- Send a review request through the selected channel with a round identifier, the exact base and tip commit IDs or immutable snapshot identifier, the scope, and the complete review criteria. For later rounds, include prior findings and the author's disposition of each. In Relay mode, the reviewer replies to the request and acknowledges it only after sending its result. In direct mode, follow `session-message` for each request and reply, and require a result explicitly naming the round so a submitted message is not mistaken for a completed review.
- The reviewer runs its harness's review skill against the **whole pinned change**, not just the latest fix. It returns findings ordered by severity, each with a changed line and a demonstrated affected path, or `No findings.` It also names the exact target it inspected, relevant checks it ran, and material gaps. It sends that result through the selected channel and waits for another round; in Relay mode it restores one listener. It does not end the session after a non-clean round.
- The author verifies the load-bearing findings against code, fixes accepted defects in the change's own worktree (for a branch a subagent built, that branch's worktree, as `review-loop` says), and sends a new immutable target. If the invoking session is not the author, route findings to the author by its exact Relay slug or verified native or tmux address, according to the selected channel, and wait for its new target. If a finding is disputed, send the code evidence back to the same reviewer for a ruling. Treat a finding that calls for a major decision with a real alternative as `review-loop`'s Escalate disposition directs, and keep running rounds on the rest. Continue until the stop level is met; impose no fixed round or finding count.
- A result is stale if the reviewed base, tip, snapshot, or review criteria differ from the intended change. Re-run the full review on the new target. A result is **clean** only when it meets the stop level, the reviewer completed the selected review, the author independently verifies that the intended target still matches the reported IDs and includes all intended changes, and every prior finding has a disposition the stop level allows: fixed; withdrawn by the reviewer after a dispute; or declined or deferred with a reason, which at the fully-clean level needs the reviewer's or the user's agreement. At the one-pass level, the author checks its own trivial fixes and the round's result still counts for the new tip; only a non-trivial fix gets another round. A test gap that is itself actionable is a finding; other gaps are reported as residual risk.

## Keep and close the session

Keep the reviewer process alive between rounds and its Relay listener active in Relay mode. If it exits while work remains, resume **that session** using its recorded identity, as `new-session` §5 describes; do not start a fresh reviewer and lose its findings. Keep the invoking session's listener active in Relay mode as `session-message` requires. A genuine blocker can pause fixes, but the reviewer remains available and the user sees the blocker.

Once the latest target is clean, send a close request through the selected channel naming the clean round and commit IDs. The reviewer replies that its result is final and it is ready to close, acknowledging the request only then in Relay mode. Verify the reply and the pinned tmux window identity before closing that window; remove only the reviewer's own temporary worktree or scratch artifacts. If the reviewer exits itself, verify its window is gone. Report the clean target, review scope, remaining test gaps, and that the reviewer session closed.
